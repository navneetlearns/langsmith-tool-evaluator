## 2. Root cause of the improvement — live tool-surface change ⚠️

The agent's real tool surface is **no longer the documented 4-tool allow-list**
(`search_customers_master`, `getCustomerAccountData`, `getCustomerAnalytics`, `get_sales`).

Tool calls observed across v2 (80 queries):

| Tool | v1 count | v2 count | Note |
|---|---|---|---|
| **get_receivables** | 0 | **41** | NEW since v1 — dominant receivables/ageing/overdue tool |
| getCustomerAnalytics | 11 | 9 | rankings / outstanding aggregation |
| **get_collections** | 0 | **8** | NEW since v1 — month/quarter collections comparison |
| search_customers_master | 4 | 8 | customer lookup/resolution |
| getCustomerAccountData | 2 | 2 | per-customer account detail |

`get_receivables` (mode=customer_detail / ageing buckets) + `get_collections` are **not in the
documented allow-list**. Their arrival is what unlocked the Overdue & Aging, collection
follow-up, and trend categories. **Action for agent owners:** update the system-prompt
allow-list / deployed-chat-templates doc to include `get_receivables` and `get_collections`
(the collection_and_account_receivables agent clearly ships with them now). `get_sales` still
never appears in this account's traces.

## 3. Tool-accuracy — raw vs. corrected

**Raw (against the 2026-09-07 expected_tool labels in queries.xlsx):**
- Strict (exact tool-name match): **26/80 = 32.5%**
- Lenient (any real data call on TOOL-expected): **32/80 = 40.0%**

**These raw numbers UNDERSTATE the agent** and should NOT be read as "agent is 32% correct."
The expected_tool mapping is stale relative to the new capability:

- The 24 TOOL-expected labels name `getCustomerAnalytics` / `getCustomerAccountData`, but the
  agent now answers those query intents with `get_receivables` (correct behavior, different
  tool name → scored a strict mismatch). Re-scored for intent, those are real data calls.
- Of the 24 TOOL-expected, 8 made NO tool call — all are historical/trend/average queries
  ("changed over last 6 months", "monthly outstanding trend", "average outstanding per
  customer", "contributed to increase", "unusual increases", "balance vs historical
  average") that the agent **correctly refuses** because date-scoped/historical data is not
  exposed by `get_receivables`/`get_collections`. These are eval-mapping over-expectations
  (same class as the v1 lesson: "FIX THE MAPPING, not the agent").
- The 56 NO_TOOL labels are now largely WRONG: **40 of them** were answered with a real tool
  call because the agent gained the ability (see §4). These are capability expansions, not
  tool-adherence drift.

**Corrected tool-selection grade** (judged against what the agent can legitimately do today):
the agent reliably calls a real data tool when one can satisfy the query, and safely refuses
the handful of genuinely-unsupported ones (historical payment *behavior* patterns → no tool +
"cannot"). No malicious/ad-hoc out-of-scope tool use seen in v2 (the v1 `get_channel_data` /
`get_thread_messages` drift calls did NOT recur).

**Recommendation:** regenerate the expected_tool mapping for v3 from the CURRENT real surface
(get_receivables / get_collections / getCustomerAnalytics / getCustomerAccountData /
search_customers_master), marking TOOL for the now-answerable categories and keeping NO_TOOL
only for true refusals (payment-behavior history, some trend/average). The generator
(`scripts/gen_collections_queries.py`) is the single source of truth for the mapping.
